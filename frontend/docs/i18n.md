# i18n (Internationalization)

MedConnect is internationalized with [next-intl](https://next-intl.dev) using the
**"App Router without i18n routing"** setup: there is **no `[locale]` URL
segment** — all portals keep their existing routes (`/patient/*`, `/doctor/*`,
`/admin/*`), and the active locale is stored in the `NEXT_LOCALE` cookie.

Shipped locales: **English (`en`)** and **Hindi (`hi`)**. English is the default
and the source of truth for message keys.

## How it works

| Piece | File | Purpose |
|---|---|---|
| Request config | `src/i18n/request.ts` | `getRequestConfig` — reads `NEXT_LOCALE` cookie, falls back to `en`, loads `messages/<locale>.json` |
| Locale registry | `src/i18n/locale.ts` | `LOCALES`, `DEFAULT_LOCALE`, `LOCALE_COOKIE`, `LOCALE_LABELS`, `isLocale()` — shared by server + client |
| Plugin | `next.config.js` | `createNextIntlPlugin('./src/i18n/request.ts')` wraps the Next config |
| Provider | `src/app/layout.tsx` | `await getLocale()` sets `<html lang>`; `NextIntlClientProvider` (no props — inherits locale + messages from the request config) wraps the app |
| Messages | `messages/en.json`, `messages/hi.json` | ICU messages, grouped by namespace (`nav`, `timeline`, …) |
| Switcher | `src/components/layout/language-switcher.tsx` | EN/HI toggle — writes the cookie + `router.refresh()` |
| Types | `global.ts` | Augments `next-intl`'s `AppConfig` → type-checked keys + `Locale` |

The locale switcher currently lives in the **patient sidebar footer**
(`patient-sidebar.tsx`). Mount `LanguageSwitcher` anywhere else the same way —
it is a plain client component.

## Adding a translated string

1. Add the key to `messages/en.json` under a namespace, e.g.
   `"records": { "title": "Medical Records" }`.
2. Add the same key to `messages/hi.json` (all locales must have identical key
   sets — missing keys throw `IntlError` at render time).
3. Use it:

   ```tsx
   // Client component
   "use client";
   import { useTranslations } from "next-intl";
   const t = useTranslations("records");
   <h1>{t("title")}</h1>

   // Server component (async)
   import { getTranslations } from "next-intl/server";
   const t = await getTranslations("records");
   ```

   Interpolation: `t("byDoctor", { name: doctor.name })` ↔ `"by {name}"` in the
   JSON (ICU plural/select syntax also supported).

Key names are **compile-time checked** against `en.json` — a typo is a type
error, not a runtime surprise. For data-driven lists, store the *key* in the
array (see `navSections` in `patient-sidebar.tsx`, `RECORD_TYPES` in the
timeline page) instead of a literal label.

## Adding a locale

1. `messages/<locale>.json` — copy `en.json`, translate the values.
2. Add the locale to `LOCALES` and `LOCALE_LABELS` in `src/i18n/locale.ts`
   (native-script label, e.g. `"ta": "தமிழ்"`).

That's it — the switcher picks it up automatically, and the request config
validates cookie values via `isLocale()`.

## Coverage & roadmap

Translated now (proof of scaffold): **patient sidebar nav + logout + aria
labels**, **patient timeline page** (title, filters, empty state, badges,
pagination), and the language switcher itself.

Not yet translated — the remaining ~70 pages across patient/doctor/admin
portals, shared components (`Breadcrumb`, `PrescriptionCard`, record-type
labels in `lib/utils.ts`), Keycloak-hosted login/OTP screens, date/number
formatting (`formatDate` → `useFormatter().dateTime`/`format.number` for
`hi-IN` digits/formats), and metadata (`<title>`, manifest).

Known trade-offs:

- **Cookie-based locale ⇒ dynamic rendering.** `getRequestConfig` reads
  `cookies()`, so routes rendering translations opt out of full static
  prerendering. Accepted cost of not having locale URLs.
- **All messages ship to every client.** `NextIntlClientProvider` inherits the
  full message bundle — fine at current size (~40 keys); split per-namespace if
  the bundle grows.
- **Cookie is not httpOnly** (the switcher writes it from JS). If locale moves
  to the user profile later, set it server-side during login instead.
- If SEO ever requires localized URLs, migrate to next-intl's `[locale]`
  segment routing — messages and `t()` calls carry over unchanged.
